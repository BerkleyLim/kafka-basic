# 03. 프로듀서와 컨슈머 (Step 01 ~ 04)

## Step 01 — 토픽 만들기 · `./gradlew topic`

`Admin` 클라이언트로 `device-events`(파티션 3)와 `device-events.DLT`(파티션 1)를 만든다.

```
브로커 localhost:9092 에 연결            ← 엉뚱한 브로커가 아닌지 먼저 본다
토픽 생성: device-events (파티션 3)
── device-events ──
  partition=0 leader=1 replicas=1 isr=1
```

docker-compose 는 `auto.create.topics.enable=false` 다. 오타 난 토픽 이름으로 보내면 토픽이 새로 생기는 대신 에러가 난다. 운영에서도 보통 이렇게 둔다.

## Step 02 — 보내기 · `./gradlew produce -Pargs="9"`

```
보냄 key=device-A → partition=0 offset=0
보냄 key=device-B → partition=0 offset=1
보냄 key=device-C → partition=1 offset=0
```

볼 것
- **같은 키는 항상 같은 파티션.** device-A 는 몇 번을 돌려도 partition 0.
- **offset 은 파티션마다 따로** 센다.
- device-A, device-B 가 둘 다 partition 0 이다. 키 해시가 고르게 나뉜다는 보장은 없다.

설정 (`SimpleProducer.producerProps()`)

| 설정 | 값 | 이유 |
|---|---|---|
| `acks` | `all` | 리더 + ISR 모두 받아야 성공 |
| `enable.idempotence` | `true` | 재전송으로 같은 메시지가 두 번 쓰이는 걸 브로커가 막는다 |
| `linger.ms` | `5` | 5ms 모아서 한 번에 → 처리량 |

`send()` 는 바로 돌아온다. 결과는 콜백으로 오고, 콜백은 프로듀서의 I/O 스레드에서 돈다 — 콜백 안에서 무거운 일을 하면 전송 전체가 느려진다.

## Step 03 — 받기 · `./gradlew consume`

```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));
    for (var record : records) { /* 처리 */ }
    if (!records.isEmpty()) consumer.commitSync();   // 처리 후 커밋
}
```

해 볼 것
1. 실행 → 지금까지 보낸 메시지가 다 나온다 (`auto.offset.reset=earliest`)
2. Ctrl+C 로 끄고 다시 실행 → **아무것도 안 나온다.** 커밋한 위치부터 읽기 때문
3. `./gradlew consume -Pargs="other"` → 그룹이 다르니 처음부터 다시 나온다

**안전한 종료**: `KafkaConsumer` 는 스레드 안전하지 않다. 다른 스레드에서 부를 수 있는 건 `wakeup()` 뿐이다.
종료 훅에서 `wakeup()` → `poll()` 이 `WakeupException` 을 던짐 → 메인 스레드가 정리하고 `close()`.
`close()` 를 해야 그룹을 바로 떠나고, 남은 소비자가 기다리지 않고 리밸런스한다.

## Step 04 — 소비자 그룹 · `./gradlew group -Pargs="worker-1"`

터미널 세 개:

```bash
./gradlew group -Pargs="worker-1"
./gradlew group -Pargs="worker-2"
./gradlew produce -Pargs="30"
```

실제 실행 기록 (worker-1 먼저, worker-2 참가, worker-1 종료):

```
[worker-1] 배정 [device-events-0, device-events-1, device-events-2]
[worker-1] 반납 [device-events-0, device-events-1, device-events-2] → 처리분 커밋   ← worker-2 참가
[worker-1] 배정 [device-events-0, device-events-1]
[worker-2] 배정 [device-events-2]
...
[worker-1] 반납 [device-events-0, device-events-1] → 처리분 커밋                   ← worker-1 종료
[worker-2] 반납 [device-events-2]
[worker-2] 배정 [device-events-0, device-events-1, device-events-2]
```

볼 것
- 소비자 수 ≤ 파티션 수 일 때만 늘린 만큼 빨라진다. 4번째 소비자는 배정이 비어 있다.
- **`onPartitionsRevoked` 에서 커밋**한다. 안 하면 새 주인이 마지막 커밋 위치부터 다시 읽어 중복 처리가 생긴다.
- 위 기록에서 worker-2 가 들어올 때 worker-1 이 **세 개를 다 반납했다가** 두 개를 다시 받는다. 이게 기본(classic, eager) 리밸런스 방식이다. 리밸런스 동안 그룹 전체가 멈춘다.

### 리밸런스 방식

| 방식 | 설정 | 특징 |
|---|---|---|
| Eager (기본 classic) | 기본값 | 전부 반납 → 다시 배정. 단순하지만 멈춤이 길다 |
| Cooperative sticky | `partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor` | 옮길 파티션만 반납 |
| 새 그룹 프로토콜 (KIP-848) | `group.protocol=consumer` | 브로커가 배정을 주도. Kafka 4.0 부터 정식 |

설정 한 줄로 바꿔서 위 기록이 어떻게 달라지는지 비교해 보면 좋다.
