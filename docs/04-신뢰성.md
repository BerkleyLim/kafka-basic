## 1. 전달 보장

| 이름 | 뜻 | 만드는 법 |
|---|---|---|
| at-most-once | 많아야 한 번. 유실 가능 | 처리 전에 커밋 |
| **at-least-once** | 적어도 한 번. **중복 가능** | 처리 후에 커밋 ← 이 저장소 |
| exactly-once | 정확히 한 번 | Kafka → Kafka 구간은 트랜잭션으로 가능. 외부 DB 까지 묶으려면 결국 멱등 처리가 필요 |

현실적인 답은 거의 항상 **at-least-once + 멱등 처리**다.

## 2. 실패를 세 가지로 나눈다

`ReliableProcessor.handle()` 의 흐름:

```
JSON 파싱 실패 ─────────────────────────────▶ DLT        (영구 실패: 다시 해도 안 됨)
이미 처리한 eventId ────────────────────────▶ 건너뜀     (중복)
처리
 ├ PermanentFailure (말이 안 되는 값) ───────▶ DLT
 ├ TransientFailure (일시 장애) ─▶ 기다렸다 재시도 ─▶ 성공 / 횟수 초과 시 DLT
 └ 성공 ──────────────────────────────────▶ eventId 기록
```

| 종류 | 예 | 처리 |
|---|---|---|
| 중복 | 같은 eventId 가 또 옴 | 건너뛴다 |
| 일시적 | DB 순간 끊김, 외부 API 타임아웃 | 백오프하며 몇 번 재시도 |
| 영구적 | 깨진 JSON, 말이 안 되는 값 | **바로 DLT.** 재시도해 봐야 시간만 쓰고 파티션이 멈춘다 |

영구 실패를 계속 재시도하면 그 한 건 때문에 뒤의 메시지가 전부 막힌다. 이런 메시지를 **poison pill** 이라 부른다.

## 3. DLT (Dead Letter Topic)

- 원본 키 · 값을 **그대로** 옮기고, 이유와 원래 위치는 **헤더**에 적는다.
- DLT 전송은 **동기**(`.get()`)로 한다. DLT 저장이 확인되기 전에 원본 offset 을 커밋하면 메시지가 사라진다.
- DLT 에도 못 넣으면 예외를 올려 소비를 멈춘다 → 커밋되지 않으니 다시 켜면 다시 받는다.

DLT 확인:

```bash
docker exec kafka-basic /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:19092 \
  --topic device-events.DLT --from-beginning \
  --formatter-property print.headers=true --formatter-property print.key=true
```

실제 출력:

```
dlt.reason:JSON 아님: Unexpected character ('t' …),dlt.original.topic:device-events,dlt.original.partition:0,dlt.original.offset:2	device-B	{this is not json
dlt.reason:절대영도보다 낮은 온도: -999.0,dlt.original.topic:device-events,dlt.original.partition:0,dlt.original.offset:3	device-B	{"eventId":"…","value":-999.0,…}
```

## 4. 멱등 처리 — 실습과 실무의 차이

실습은 처리한 eventId 를 **메모리 Set** 에 둔다. 재시작하면 잊는다.

실무에서는:

```sql
-- 처리 결과를 쓰는 같은 트랜잭션 안에서
INSERT INTO processed_event (event_id, processed_at) VALUES (?, now());   -- event_id 에 유일 제약
-- 유일 제약 위반 → 이미 처리한 것 → 건너뜀
```

처리 결과와 "처리했다" 기록이 **같은 트랜잭션**이어야 한다. 따로 쓰면 그 사이에 죽었을 때 또 어긋난다.

## 5. 재시도 위치

이 실습은 소비 루프 안에서 잠깐 쉬었다 재시도한다(blocking retry). 간단하지만 그동안 그 파티션이 멈춘다.
재시도가 길어지면 `max.poll.interval.ms`(기본 5분)를 넘겨 그룹에서 쫓겨난다.

더 길게 기다려야 하면 재시도 토픽(`device-events.retry-1m` 등)으로 보내고 다른 소비자가 나중에 처리하는 방식(non-blocking retry)을 쓴다. 대신 그 메시지는 순서를 잃는다.
